# LabLink · 产品案例

## 问题与目标

企业的技术问题与高校团队的研究表达存在语言差异。原型希望验证：先结构化描述问题，再解释研究能力相关性，是否能让合作讨论更容易开始。

## 三个产品取舍

| 决策 | 原因 | 代价与待验证内容 |
| --- | --- | --- |
| 先做可解释的关键词规则 | 让拆解路径可观察，便于演示和修正 | 同义表达和复杂需求覆盖有限 |
| 用公开研究资料解释相关性 | 让候选团队不只是名称和标签 | 公开资料不证明承接意愿与产业交付能力 |
| 将沟通关联到具体需求 | 保留背景、交付条件与讨论上下文 | 真实协作仍需身份、权限和跨用户消息能力 |

## 案例 A：开裂与失效分析

**示例输入：** “产品反复开裂，希望做失效分析，查清材料和工艺因素。”

当前 `server/analysis.mjs` 的词项映射包含：

| 输入线索 | 对应能力标签 |
| --- | --- |
| 裂纹、断裂、开裂、失效 | 断口分析、材料表征 |
| 加工、工艺、刀具、机床、精密 | 加工质量控制 |

此输入可命中以上规则。标签用于组织候选与讨论方向，不能视为完成工程诊断。随后需要补充样品、失效条件、已有测试、验收标准与周期。

## 案例 B：公开 PI 档案

本地原型使用褚驰恒公开主页及论文链接，演示“公开研究方向 → 企业可讨论问题”的表达。页面标记档案尚未认领；设备、团队人员、承接周期和预算不作为已确认信息。

原型资料记录的来源入口包括[浙江大学主页](https://person.zju.edu.cn/chihengchu)和 [Water Research 论文 DOI](https://doi.org/10.1016/j.watres.2023.120674)。本案例仅说明原型如何组织来源，不新增对论文内容或团队承接能力的判断。

## 实现与规划

- **本地已实现：** 双身份演示、需求字段、规则拆解、团队档案、匹配解释、收藏、应征、邀请、本地聊天与 SQLite 保存。
- **未在本仓库发布：** 应用源码、可运行包与演示数据库。
- **后续方向：** 身份认领与权限、语义匹配、真实消息投递和合作结果跟踪。
- **尚未证实：** 企业付费意愿、真实撮合率、合作交付效果。

## 评估计划

使用经同意收集的企业需求样本，让相关领域人员评价拆解标签与候选相关性。记录需求填写完成情况、缺失字段、候选解释理解情况与继续沟通意愿。

真实双边试点应单独跟踪邀请、响应、需求澄清和合作推进，明确每一步分母。原型页面点击与本地留言不能替代真实撮合指标。
